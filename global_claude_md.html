Communicating with me

I'm a human and my time is my most valuable asset. For a model it's trivial to write walls of explainer text and read a billion tokens; for me it is not. At every human-in-the-loop touchpoint (end-of-sprint summaries, handovers, questions) every token must earn its place:

  • Concise and clear over exhaustive. I'm a technical dev, but I didn't watch what you did or solved: frame it cleanly with specific examples (a before/after, one representative snippet) rather than narrating everything. Keep the summary self-contained; don't make me open other files to understand it.
  • No unnecessary verbosity, but also no hyper-dense prose I have to read twice. Plain sentences, jargon only where it's the precise term.
  • Never use a bare pointer or ID as if I remember what it means. Task numbers, phase numbers, ticket codes, doc anchors (3.2, C13, Thread-C, file/section refs) live in your context, not mine. The docs/ plan files are written for you, the agent; I almost never open them. The only thing I read is what you produce in the session. So whenever you reference something from a doc, restate it inline in a sentence: what it is, what the problem is, what the doc proposed. Keep the pointer, just never naked:
    Bare pointer"Pull task 3.2 forward — it needs no prod rows. The engine-envelope design (C13) …"
    Pointer with a hook"Pull task 3.2 (backfill the embeddings index) forward — it needs no prod rows. The engine-envelope design — C13, which atom envelope feeds the shareable bio — …"
  • Use rich visual markdown (headers, tables, bold, code blocks) to make summaries scannable and fast to absorb.

My machine

  • M2 MacBook Pro (Apple Silicon).
  • When running ffmpeg locally, always use Apple VideoToolbox hardware acceleration: -c:v h264_videotoolbox instead of libx264, -c:v hevc_videotoolbox instead of libx265.

Python tooling

  • I use uv for everything, by default, across all projects: uv run, uv add, uv sync, uvx. Not bare pip, not python -m venv, not poetry, not conda.
  • For linting and dead-code checks, use ruff. Not pyflakes; it isn't installed on this system.

Modal SDK

  • To copy local directories into a Modal image, use .add_local_dir(local_path, remote_path=...). .copy_local_dir() does not exist.
  • The official Modal skill ships inside the modal PyPI package and does not auto-refresh. Its API reference is generated from whichever version was installed at install time, so it silently drifts. Whenever you upgrade modal in any project, run uv run modal skills update --claude -g --yes as part of the same task. The newest SDK on disk wins.

Fallow, the truth layer for TS/JS

fallow is installed globally: a deterministic, graph-based static analyzer that finds dead code, duplication, complexity hotspots and architecture drift across the whole module graph. Use it as the truth layer to verify AI-generated changes.

fallow audit                    # before every commit in a TS/JS repo: pass / warn / fail
fallow dupes --mode semantic    # when suspecting duplicated logic; semantic catches renames

Repo markdown docs: the docs/ workflow

Most of my repos have a docs/ folder full of markdown files that I treat as living working memory for coding agents. Three subfolders:

FolderWhat lives thereLifecycle
docs/TODO/Implementation plans, future features, the roadmap. Short-lived, churns fast.Where new features start their life.
docs/reference/How things actually work right now, and why. Always up to date with what exists.Where features end up once built.
docs/finished/Deprecated docs, retired plans.Write-only from your perspective: move files in, never read from.

A reference doc is a map, not a mirror: it exists so an agent knows which files to read and why. Where the relevant code lives, what role each file plays in the bigger picture, and the reasoning behind past design decisions so mistakes aren't repeated. It briefs the read; it doesn't replace it. Its job is to get an agent oriented fast, in far fewer tokens than reading the code cold, so a clean restatement of how a subsystem fits together earns its place even if it could in theory be derived from the code. What doesn't earn its place: line-by-line narration, function-signature listings, and mirrors of code that will drift the moment the code changes. Always add what the code can't tell you: why it's shaped this way, what was tried and rejected, which invariants are load-bearing, where the traps are.

The test for a section: does this help an agent decide what to read and how to change it faster than the code itself would? If yes, keep it.

Reference docs follow code, never lead it. Don't pre-write docs/reference/<feature>.md for something that doesn't exist yet; that's what docs/TODO/ is for. The moment a reference doc starts describing aspirational behaviour, it becomes a lie the next agent will believe.

Lifecycle: new work appears in docs/TODO/ first. As it ships, the durable bits migrate into docs/reference/. Once a plan is fully drained, the husk moves to docs/finished/. The job of every doc-update pass is to keep the overlap between them small and directional: TODO shrinks, reference grows.

These docs are the primary briefing material I point agents at. Keeping them up to date is every single agent's job, not a separate task: whenever you notice a doc is out of date versus the code, you fix that doc in the same session. Don't leave it for the next agent. Stale docs are worse than no docs, because they mislead the next agent.

The repo-root CLAUDE.md: what it is and how to maintain it

What it is: the map an agent reads cold at first contact. The mission, conventions, commands, repo layout, the load-bearing cross-cutting rules and gotchas needed every time, and a pointer map into docs/reference/. The reference docs are per-feature deep context, loaded when relevant. They point at each other, never duplicate each other.

What it is not: an encyclopedia, a changelog, a sprint log, or an incident archive. Per-feature depth belongs in a reference doc; in-flight plans belong in docs/TODO/; history belongs in git.

Two hard rules govern what it links to

  • Every reference doc gets a pointer.
  • Do not list docs/TODO/ sprint docs in it. I always point an agent at a specific sprint doc by hand when I start a session, so a single stable pointer to the folder itself is fine.

When to update it

After changes that shift the map: a route, top-level package, deploy surface, or reference doc added or removed.

The bar for every sentence: would a future agent landing cold be misled without it? If no, it doesn't belong there.

Rules that keep it from bloating

  • New feature → reference doc + one pointer line, never a new prose section. More than ~3 sentences about one subsystem = a reference doc in the wrong file.
  • No status markers or datelines as content ("FIXED 2026-…", "Phase X COMPLETE"). Describe the steady state.
  • Only cross-cutting gotchas (likely to bite in most sessions) belong here. When adding, also subtract.
  • Size budget ~5,000 words. Over budget → move detail into docs/reference/, don't grow the file.

When to update docs

Do a doc pass at the end of an implementation phase (shipped feature, refactor, public-API change, dependency change, architectural decision) before declaring the task done. It's part of the task, not a follow-up. Trivial fixes skip it. Two standing rules:

  • Drift is a shared burden: if your task crosses paths with a doc that's materially misleading, fix it with a short corrective edit. Don't let cleanup eclipse the actual task.
  • Code is the source of truth: when code and a doc disagree, the doc is stale. Update the doc, never "fix" working code to match it (unless I explicitly framed the doc as a spec).

Maintaining a sprint plan as work progresses

A plan doc briefs the next agent; it is not a historical log. Completed phases must be actively drained, not just checked off. Mandatory condensation pass when you finish a phase:

  1. Promote durable detail into docs/reference/. Information flows TODO → reference, never back.
  2. Collapse each completed phase to a few lines: what shipped, key names and locations, decisions that constrain remaining work, plus a Done, see reference/<feature>.md pointer.
  3. Delete scaffolding: code snippets, rejected options, debug notes, fully-checked checklists.
  4. Keep still-open sections (next steps, open questions, known issues) verbatim and clearly marked.
Test for a well-drained doc: open work reachable in the first screenful, and the shipped-work section shorter than the remaining-work section.

Scope discipline across files

One file = one pure scope. No fact restated across files, no catch-all god-files. When two docs overlap: pick the canonical home, leave a one-line pointer in the other, delete the duplicate prose. Cross-link liberally with relative paths.

Closing out a finished plan

  1. Promote durable knowledge into docs/reference/ (create the doc if needed).
  2. Re-home leftover TODOs into other open plans that fit their scope.
  3. Move the husk to docs/finished/. Move, never delete, unless I explicitly said so for that file.
  4. Fix dangling links: none may point into docs/finished/.

Before declaring a coding task done

  • Docs invalidated by this change updated; if working off a TODO plan, condensation pass run (TODO shrinks, reference grows).
  • Every reference doc has a pointer in CLAUDE.md; no TODO sprint docs enumerated there.
  • Finished plans: TODOs re-homed, husk moved to docs/finished/, no dangling links.

Time estimates for dev work

Modern AI-assisted dev: fast-path tasks (codegen from specs, refactoring, boilerplate) are ~10× faster; normal-path tasks (architecture, debugging, iterative human-in-the-loop feedback) are ~2× faster. Weight estimates toward normal-path rather than a blanket speedup.

Cut for the room: a personal-goals file this one also loads, so every task nests under what I'm actually trying to do this year

That's the whole trick. Anything you'd explain to a new colleague on day one belongs in a file like this. Start with three rules, and add one every time you catch yourself saying something twice.
