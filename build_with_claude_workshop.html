Strip it down: the model is a function from text to text. It has read a lot, so it guesses well. But it can't do anything: no internet, no files, no clock, no memory once the call ends. Every superpower an agent has must be built out of this one text-in, text-out machine. Keep the umbrella example running through the next three slides.

Under the hood · 2 of 4
So how can a text machine use a tool?

A tool is a description in the window.
A tool call is just text the model writes.

the context window
setupYou have one tool. To use it, write exactly: <call>get_weather("city")</call> get_weather — returns the current weather for a city.← plain text
youDo I need an umbrella in Ghent today?
model<call>get_weather("Ghent")</call>← generated, token by token
 …and then it stops. Nothing has happened yet.
1 · The tool is text
Its name, what it does, and how to write a call are pasted into the window before the conversation starts. The model reads them like any other sentence.
2 · The call is text
When the model decides it needs the tool, it writes the call — name plus arguments — in the agreed format. It's predicting tokens, exactly as it predicted "Brussels".
3 · Nothing ran
The model has no hands. It produced a string that looks like a function call. Someone has to notice that string and act on it.

This is the moment people get it: the model never "calls" anything. It reads a text description of a tool, and when it wants the tool it writes a call as text, in the format it was told. Then it stops. Point at the blank line: nothing has happened yet.

while True:

Ten lines of plain code. It looks at the model's output, spots the call, runs the real function, appends the result to the window as text, and calls the model again. That's the whole trick.

The harness is boring code: read the output, regex for the call, run the real function, append the result, call the model again. Claude Code is exactly this loop with more tools. Emphasise: the model never touches the world, the harness does, and everything the harness does is visible in the window afterwards.

Under the hood · 4 of 4
Put together, that is the entire definition of an agent

A model. Some tools.
A loop.

1
the model
Think
Reads the whole window — goal, tool descriptions, everything so far — and writes text: an answer, or a tool call.
2
the harness
Act
Code spots the call and runs the real thing: read a file, run a command, search the web, hit an API.
3
the window
Observe
The result comes back as text, appended to the window. Done? Stop. Not done? Back to 1.
A chatbot stops after think. An agent runs the loop.

Everything else people hear about — memory, planning, "autonomy", multi-agent — is this same loop with better tools and a longer leash. And the model only ever writes text: that's why you can safely hand it more and more tools.

Now show a real tool call happening: open Claude Code, ask something that needs a file read, narrate: "that's the model deciding, that's the tool call, that's the result coming back into the window." Plant the seed for the next slide: everything it knows about your problem is whatever is inside that one window right now.

Communicating with me

I'm a human and my time is my most valuable asset. For a model it's trivial to write walls of text; for me it is not. At every human touchpoint, every token must earn its place:

  • Concise and clear over exhaustive. I didn't watch what you did — frame it with one representative example (a before/after, one snippet) rather than narrating everything.
  • Never use a bare pointer as if I remember it. Task numbers, section refs and ticket ids live in your context, not mine. Restate what it is inline, the first time.
  • Rich visual markdown — headers, tables, bold, code blocks — so summaries are scannable.

Python tooling

I use uv for everything: uv run, uv add, uv sync — not bare pip, venv, poetry or conda. Lint with ruff, never pyflakes.

Repo docs are the agent's working memory

Three folders: docs/TODO/ (plans, where work starts) → docs/reference/ (how things work now, and why) → docs/finished/ (write-only archive). A reference doc is a map, not a mirror: which files to read and why, what was tried and rejected, which invariants are load-bearing. Anything the code already says is redundant and a drift surface.

Reference docs follow code, never lead it. When a doc and the code disagree, the doc is stale — fix the doc.

Three times it went wrong.

  1. 1
    It confidently fixed the wrong thing
    Because I hadn't read the plan before it built. Lesson: step 1 exists so you read before it builds.
  2. 2
    It worked locally and silently did nothing in prod
    A setting defaulted to "off" because a secret never shipped. Lesson: "it ran" is not "it's verified". Ask it how it knows.
  3. 3
    It built on a feature that had been removed
    A doc still described it; the agent trusted the doc for an hour. Lesson: stale context is worse than none — the model believes the window.

Two on stage, three if there's time. If running late, drop story 3 first (its lesson already landed on the progressive-disclosure slide).

Cheat sheet

Starter prompts.

  1. 00Rung 0 · Setup

    Make a file in this folder called hello.md that lists three things you could help me with today, based on what you can see about this machine. Keep it short, then tell me how to open it.

  2. 01Rung 1 · First build

    I'm a complete beginner. I want a single-page web app in this folder, no backend, that I can open in my browser: a personal "what should I work on today" board. Propose a plan first and wait for my ok. Then build in small steps, explain each in one line, ask me before adding anything I didn't mention, and tell me how to open it when done.

  3. 02Rung 2 · Plug in

    I want to connect an MCP server so you can use my browser. Walk me through it step by step, check it's working, then use it to open my app, click around, and tell me three things you'd improve. Don't change anything until I say so.

  4. 03Rung 3 · Give it context

    Three files, show me each before saving. 1: a global ~/.claude/CLAUDE.md with three rules on how to talk to me (concise, lead with the answer, one example not a narration), my toolchain, and "ask before anything destructive". 2: a CLAUDE.md for this project — what it is, how it's laid out, three rules — no narrating the code. 3: a skill at .claude/skills/add-feature/SKILL.md that captures my preferred way of adding a feature, with a one-line description and a body.

  5. 04Rung 4 · Free build, grilled

    Here's something I've always wanted to exist: [describe it in two sentences]. Grill me — one round at a time, your recommended answer next to every question, don't build until we agree. After that: a plan in five steps, flag the hardest part, then we build step one together.

Click a prompt, or press 0 – 4, to copy it

Leave this on the projector for the whole build. Rung 2 default = the browser MCP (strongest "it just did that?" moment, no keys); filesystem MCP as fallback. The grilling skill file for rung 4 is in the pack.
